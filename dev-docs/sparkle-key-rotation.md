# macOS Sparkle EdDSA Key Rotation (safe / no stranded users)

Rotate the Sparkle signing key **without breaking auto-update** for people
already running an old build. macOS only — Windows is a separate track and is
not touched here.

## Why this is a two-phase rollout

Sparkle 2.x (we ship **2.9.0-beta.2**) enforces the EdDSA signature: every
installed app verifies each update's `sparkle:edSignature` against the
`SUPublicEDKey` **baked into the copy the user is currently running**. If we
just swap the key and sign the next release with a new key, every existing
install rejects it and is stranded — Developer ID is an *additional* check, not
a fallback for the EdDSA key.

So:

- **Phase 1 — intermediate release (`2026.07.21`):** built with the **NEW**
  public key in its `Info.plist`, but its installer signature is made with the
  **OLD** private key. Old-key users accept it (old-key signature verifies) and,
  once installed, now trust the new key.
- **Phase 2 — next release:** signed with the **NEW** private key. Publish it
  only **after** the intermediate has been adopted — do not list both in the
  appcast at once, or an old-key user will see the newer Phase-2 item, fail to
  verify it, and get stuck.

```
old-key install ──(2026.07.21, signed OLD, carries NEW pubkey)──▶ new-key install ──(Phase 2, signed NEW)──▶ …
```

## Keys (already set up)

Sparkle 2.x stores the signing key as the base64 of the 32-byte Ed25519 seed in
a Keychain generic-password item (service `https://sparkle-project.org`). Both
keys now coexist under different **accounts**, so nothing had to be deleted:

| Account | Key | Public key (`SUPublicEDKey`) |
|---|---|---|
| `ed25519` | OLD | `2eiUHVoMgl+qqhEWO8iix5SUcRAKfkWYESh9F7jG6ls=` |
| `ed25519-v2` | NEW | `rQM13H6rUc0dBXqLdQdZgjNs5qGn+TF/uvSvxOc1H+4=` |

The new key was generated by `scripts/build/generate_sparkle_key.py`
(no Sparkle `generate_keys` binary required). `packaging/Resistine.spec` already
points `SUPublicEDKey` at the new key and `VERSION` at `2026.07.21`.

**Back up the new private key now** (private — never commit). Run this yourself
and store the output offline (password manager, etc.):

```bash
security find-generic-password -s 'https://sparkle-project.org' -a 'ed25519-v2' -w
```

Keep the OLD key (`ed25519`) until Phase 2 has shipped — it signs the
intermediate. After Phase 2 is out and adopted you may delete it.

## Phase 1 — build & publish the intermediate (`2026.07.21`, signed OLD)

1. Spec is ready: `SUPublicEDKey = rQM1…` (new), `VERSION = 2026.07.21`.
2. Build the notarized installer as usual:
   ```bash
   ./scripts/build/build-distribution.sh
   ```
3. Sign the installer's Sparkle signature **with the OLD key** (`ed25519`) — the
   whole point, so existing installs can verify it:
   ```bash
   ./scripts/build/sign_update --account ed25519 -p dist/Resistine-Installer.pkg
   #   → prints:  sparkle:edSignature="…" length="…"
   ```
4. **Verify before publishing** (catches a wrong-key/format mistake):
   ```bash
   ./scripts/build/sign_update --account ed25519 --verify dist/Resistine-Installer.pkg "<edSignature>"
   #   → must print OK. If not, DO NOT PUBLISH.
   ```
5. In the **resistine.github.io** repo: copy the installer to
   `releases/mac/Resistine-Desktop-Mac-2026.07.21.pkg`, then add a macOS `<item>`
   to `appcast.xml` (mirror the 2026.06.17 item — no `sparkle:os`, include
   `sparkle:minimumSystemVersion`) using the edSignature/length from step 3:
   ```xml
   <!-- macOS Version 2026.07.21 (key-rotation intermediate) -->
   <item>
     <title>Version 2026.07.21</title>
     <description><![CDATA[ <h2>What's New</h2><ul><li>…</li></ul> ]]></description>
     <pubDate>Tue, 21 Jul 2026 00:00:00 +0000</pubDate>
     <sparkle:minimumSystemVersion>13.0</sparkle:minimumSystemVersion>
     <enclosure
       url="https://resistine.github.io/releases/mac/Resistine-Desktop-Mac-2026.07.21.pkg"
       sparkle:version="2026.07.21"
       sparkle:shortVersionString="2026.07.21"
       length="<from step 3>"
       type="application/octet-stream"
       sparkle:edSignature="<from step 3>"
     />
   </item>
   ```
6. Commit + push the releases repo. Existing users update to 2026.07.21 and are
   now on the new key.

## Phase 2 — the next release (signed NEW), later

Only after the intermediate has been adopted:

1. Build the next version (spec `SUPublicEDKey` stays `rQM1…`; bump `VERSION`).
2. Sign with the **NEW** key:
   ```bash
   ./scripts/build/sign_update --account ed25519-v2 -p dist/Resistine-Installer.pkg
   ```
3. Verify (`--account ed25519-v2 --verify <pkg> "<sig>"`), add the appcast item,
   publish.

## sign_update argument order (gotcha)

Verify takes the **file first, signature second**:
`sign_update --account <acct> --verify <file> "<signature>"`.
